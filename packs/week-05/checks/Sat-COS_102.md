## Answers

**1. b — 20.** *Concept: tracing a post-test loop; the counter, not the data, decides when it ends.* Take it a pass at a time. `sum = 0, count = 0`. Pass 1: n = 3, sum = 3, count = 1; is 1 < 5? Yes, back up. Pass 2: n = 8, sum = 11, count = 2; Yes. Pass 3: n = 1, sum = 12, count = 3; Yes. Pass 4: n = 6, sum = 18, count = 4; Yes. Pass 5: n = 2, sum = 20, count = 5; is 5 < 5? **No**, so the flow leaves the loop and prints **20**. The 9 is never read — the chart stops asking. (a) 18 is the off-by-one that comes from testing the counter *before* the increment, i.e. from putting the diamond above the `count = count + 1` box, which ends the loop one pass early. (c) 29 is 20 + 9: it comes from placing the test *before* the `Enter n` box, so the final No pass is imagined to read one more number before leaving. (d) 5 is the value of `count`, not `sum` — it is the answer of someone who traced the loop correctly and then read the wrong variable out of the output parallelogram, which is why the parallelogram's label must be read as carefully as any diamond's.

**2. c — Repair lamp.** *Concept: tracing nested selection; the branch label, not the position on the page, decides the path.* Plugged in means the first diamond answers **Yes**, so the flow ignores "Plug in lamp" entirely and arrives at "Bulb burned out?". The bulb is not burned out, so that diamond answers **No**, and the No branch runs to **Repair lamp** — the outcome reached only when both questions have been answered and neither easy fix applies. (a) follows the No branch of the first decision, which is the answer for a lamp that is *not* plugged in; it is the trap for anyone who reads "the lamp does not work" as the answer to "plugged in?". (b) is the commonest tracing error of all: assuming that the line continuing straight **down** the page is the default, so that a Yes at the first diamond simply drops into the next box drawn beneath it. Position on the page decides nothing; only the label on the flowline does. (d) counts outcomes wrongly — two decisions in a chain give **three** endpoints, not two, because the second diamond splits only the Yes side of the first.

**3. c — count is never changed inside the loop.** *Concept: a loop must alter what its condition tests, or the exit branch is unreachable.* `count` is set to 0 before the loop and no box inside the loop touches it — the `count = count + 1` of the working version has been dropped from the process rectangle. So "Is count < 5?" tests 0 < 5 on every pass, answers Yes every time, and the back-arrow is taken for ever. The No branch, the Print box and the STOP are drawn on the page but no execution ever reaches them, which breaks the rule that **every path must terminate**. Note what is *not* wrong: the symbols are all correct and the decision is properly formed with two labelled exits — this chart is faultless as a drawing and fatal as an algorithm, which is exactly the kind of thing the course means by using a chart to **ascertain if the logic of the program works or not**. (a) invents work for the decision symbol; a decision **asks a question and selects a path**, it changes nothing. (b) mistakes initialisation for destruction: `sum = 0` is what makes the first `sum = sum + n` meaningful, and removing it would leave sum undefined. (d) confuses decision with process — a comparison is a decision precisely because its answer determines the path, and redrawing it as a rectangle would leave a box with two exits and no condition.

**4. c.** *Concept: fan-out belongs to the decision alone; two unlabelled exits make the chart ambiguous.* A process rectangle has **one** exit. Two lines leaving it, neither labelled, means the chart does not say which one the flow follows, and a chart that does not say is not a flowchart of anything — the whole point of the labelled branch is that the reader can always answer "where does the flow go next?". The minimal repair is a diamond above the split, carrying whatever question really decides between printing the total and printing the quantity, with its two branches labelled Yes and No. (a) is the single most common misreading of parallel arrows: two lines leaving one box are read as "do this, then do that", but sequence is drawn as a **chain** — one box, one exit, into the next box — and never as a fork. (b) treats termination as the only rule of flow; both paths do reach a STOP here, and the chart is still broken, because the rules are independent. (d) is the fan-in/fan-out reversal: **merge** takes **several lines in and gives one out**, so it is what you would use to bring the two paths back together after a decision, and it cannot create a split.

**5. b.** *Concept: converting a back-arrow into a loop keyword — UNTIL takes the exit condition, not the diamond's condition.* The chart tests **after** the body, so the body runs at least once: that is `REPEAT ... UNTIL`. The diamond's condition `count < 5` selects the **Yes** branch, which is the branch that goes **back into** the loop; `UNTIL` names the condition on which the loop **stops**, so it must carry the **negation** — `count = 5`, equivalently `NOT (count < 5)`. Trace it and both give five passes. (a) is the answer of everyone who copies the diamond's condition straight across into `UNTIL`: it says "keep going until count is less than 5", and since count is 1 after the first pass, 1 < 5 is already true and the loop exits having read a single number. That one word is the whole question. (c) inverts the condition into a **pre-test** loop: `count > 5` is false at the start (count is 0), so the body never runs at all and PRINT outputs 0, whereas the chart's body always runs at least once. (d) replaces the loop with a selection — the error of reading the back-arrow as an ordinary forward flowline, so the body is performed once if the condition holds and never repeated.

**6. a.** *Concept: converting pseudocode to symbols — I/O is a parallelogram, and ELSE is the other labelled branch, not the next box down.* `READ a, b` and both `PRINT` lines move data across the boundary of the program, so all three are **input/output (data) symbols**, drawn as parallelograms; `IF ... THEN ... ELSE` is one **decision**, with the THEN consequence on the Yes branch and the ELSE consequence on the No branch, and each branch running to its own STOP. (b) draws every step as a rectangle — the "the computer performs it, so it is a process" error; a process acts on data the program already holds, whereas READ and PRINT are exactly the crossings the parallelogram exists to mark. (c) is the fall-through error: it puts `PRINT b` after `PRINT a` on the same branch, so a > b prints **both** values, and the No branch, having nothing on it, contributes nothing. ELSE is an alternative, not a continuation. (d) draws the ELSE consequence as an annotation hanging off a dashed line, which puts it **off the flow path** entirely so that it can never execute — and leaves the diamond with a single exit, so nothing at all happens when a > b is false.

**7. b.** *Concept: parallelogram vs rectangle when converting each line.* `total <- total + price` computes a new value from data the program already holds and stores it — an **action, process or function**, so a rectangle. `DISPLAY total` sends a value out of the program to the user — **data used at the output**, so the parallelogram, the input/output or data symbol. The test is always the same: does the value cross the boundary between the program and the outside world? (a) is the standard over-generalisation — everything in a chart is something the computer carries out, so that test cannot distinguish anything, and it would leave the chart with no way to show input or output at all. (c) has the right two symbols and swaps them, reasoning from "the assignment changes data" and "displaying is an action"; both statements are true and neither is the criterion. (d) reaches for two real but wrong symbols: **preparation** marks the difference between steps preparing for work and those that actually work, which is setup such as initialising a counter, not ordinary arithmetic inside the work; and the **document** symbol shows a document's input or output, meaning an actual document, not a value shown on screen.

**8. b — 16.** *Concept: tracing a counting loop whose step is 2; the loop body runs before each test.* `i = 1, total = 0`. Pass 1: total = 0 + 1 = 1; i = 3; is 3 <= 7? Yes. Pass 2: total = 1 + 3 = 4; i = 5; Yes. Pass 3: total = 4 + 5 = 9; i = 7; Yes. Pass 4: total = 9 + 7 = 16; i = 9; is 9 <= 7? **No**, so it outputs **16** — which is 1 + 3 + 5 + 7. (a) 9 is the value of total when i has just become 7: it is the answer of someone who stops as soon as i **reaches** the limit, forgetting that the test asks `i <= 7`, so 7 itself still passes and buys one more pass through the body. (c) 25 is 16 + 9, the off-by-one in the other direction — adding i one last time after the increment that took it to 9, which is what you get if you test *before* adding rather than after. (d) is the confusion of **initialisation** with **input**: `i = 1, total = 0` is a rectangle, not a parallelogram, and a chart with no input box is perfectly traceable because everything it needs is set inside it.

**9.** *Concept: tracing a chain of decisions, and why the order of the tests is part of the algorithm.* **As drawn.** Mark **70**: at "Is mark >= 70?" 70 >= 70 is true, so the **Yes** branch — output **A**. Mark **69**: 69 >= 70 is false, so the **No** branch to the second diamond; 69 >= 50 is true, so its **Yes** branch — output **Pass**. Mark **50**: false at the first diamond, No branch; 50 >= 50 is true at the second, Yes branch — output **Pass**. Mark **49**: false at the first, No; 49 >= 50 is false at the second, so its **No** branch — output **Fail**. Note that the boundary marks 70 and 50 both go to the *higher* category, because both conditions use `>=` and not `>`. **With the diamonds swapped.** The chart now reads: INPUT mark → "Is mark >= 50?"; Yes → OUTPUT Pass → STOP; No → "Is mark >= 70?"; Yes → OUTPUT A → STOP; No → OUTPUT Fail → STOP. Mark **70**: 70 >= 50 is true, so **Pass** — the A is lost. Mark **69**: **Pass**. Mark **50**: **Pass**. Mark **49**: 49 >= 50 false, then 49 >= 70 false, so **Fail**. Three of the four outputs are unchanged and one, the 70, is now wrong; worse, **OUTPUT A has become unreachable**, because any mark that could satisfy `mark >= 70` has already satisfied `mark >= 50` and been sent down the Yes branch, so no path ever arrives at it. What this shows: in a chain of decisions the second diamond is only ever reached by data that **failed** the first, so each test silently carries the negation of all the tests above it. The order is therefore part of the algorithm, not a matter of layout — overlapping conditions must be tested from the **most restrictive to the least**, and a chart that gets the order wrong can be perfectly legal as a drawing, with every branch labelled and every path terminating, while containing a box the flow can never reach.

**10.** *Concept: finding several independent faults in one chart and naming the rule each breaks.* **Fault 1 — the decision has only one outgoing branch.** The rule is that a decision has **exactly two outgoing flowlines, both labelled** with the answer that selects them. Here only the Yes branch is drawn, so the chart says nothing whatever about what happens when n is not negative: the flow arrives at the diamond, the answer is No, and there is no line to follow. A reader can conclude what happens to a negative n; a reader can conclude **nothing** about a zero or positive n, and must not assume the chart "just carries on" or "just stops", because neither is drawn. *Minimal fix:* draw a second flowline from the diamond, labelled **No**, and route it to whatever should happen in that case — here, to the squaring step. **Fault 2 — there is no STOP, and the one path that exists is a loop that never leaves.** The rule is that **every path must terminate**, and the course's principle is that the flowchart **should have a start point and a stop point**. The OUTPUT box's flowline runs back up to INPUT n, so for a negative n the chart prints "negative", reads again, and repeats for ever with no branch out of the cycle. A reader can conclude that the chart never finishes; a reader cannot obtain any final result from it. *Minimal fix:* add a **STOP** oval and route the exit to it. If the back-arrow was intended as a retry loop it needs an exit branch; if it was not intended at all, delete it and send OUTPUT "negative" straight to STOP. **Fault 3 — the squaring step is drawn as an annotation, so it never executes.** A symbol joined by a **dashed** line is a **comment or note**: it has no flowline in and none out and is not on the flow path, so `answer = n * n` is not part of the algorithm at all, however much it looks like the point of the chart. A reader can conclude that the author intended a squaring step; a reader must conclude that as drawn it is never performed, and that `answer` is never given a value. *Minimal fix:* redraw it as a **process rectangle** on the flow path — placed on the diamond's new **No** branch, with a solid flowline in from the diamond and a solid flowline out to a parallelogram that outputs `answer`, and thence to STOP. Taken together the three faults are independent, and repairing only one of them leaves a chart that is still not traceable — which is the point of checking a chart against each rule of flow separately rather than glancing at it for plausibility.

**11.** *Concept: converting a chart with a back-arrow into pseudocode, symbol by symbol.* The pseudocode:
```
BEGIN
  count <- 1
  REPEAT
     READ price
     vat <- price * 0.075
     PRINT price, vat
     count <- count + 1
  UNTIL count > 3
END
```
Line by line, and which symbol each came from: **BEGIN / END** come from the two **terminator** ovals, START and STOP. **`count <- 1`** comes from the **process rectangle** "count = 1" — an action on data the program holds; it sits *before* REPEAT because in the chart it is above the box the back-arrow returns to. **`READ price`** comes from the **parallelogram** "READ price" — the input/output or data symbol. **`vat <- price * 0.075`** comes from the **process rectangle** "vat = price * 0.075". **`PRINT price, vat`** comes from the **parallelogram** "PRINT price, vat", output this time. **`count <- count + 1`** comes from the **process rectangle** "count = count + 1". **`REPEAT ... UNTIL count > 3`** comes from the **decision diamond** "Is count <= 3?" together with its **back-arrow**: the diamond sits at the foot of the body, so the loop is post-test and must be REPEAT rather than WHILE; the back-arrow returns to "READ price", which fixes the first line of the loop body and so where REPEAT is written; and the Yes branch is the one that repeats, so UNTIL — which names the condition for **stopping** — carries the negation of `count <= 3`, namely `count > 3`. **How many times PRINT runs: three.** Pass 1 enters with count = 1, prints, then count becomes 2, and 2 <= 3 is Yes. Pass 2 prints, count becomes 3, and 3 <= 3 is Yes — the boundary case that catches people, since `<=` lets 3 through. Pass 3 prints, count becomes 4, and 4 <= 3 is No, so the flow leaves for STOP. Three prices are read and three lines printed; note that the count runs 1, 2, 3 inside the body and reaches 4 only after the last pass, so the final value of `count` is one more than the number of prints.

**12.** *Concept: converting a pre-test sentinel loop to a chart, and why the read is drawn twice.* **The chart, symbol by symbol.** Draw a **terminator oval "START"** with one flowline out. Into a **process rectangle "total = 0"** — an assignment, so a rectangle, one line in, one out. Into a **parallelogram "READ k"** — the input/output or data symbol; this is the **priming read**. Its flowline runs into a **decision diamond "Is k <> 0?"** — one line in, **two** labelled lines out. From the diamond, the branch labelled **"No"** runs to a **parallelogram "PRINT total"**, whose flowline runs to a **terminator oval "STOP"**. The branch labelled **"Yes"** runs into a **process rectangle "total = total + k"**, whose flowline runs into a **second parallelogram "READ k"**. From that second READ box, a flowline — the **back-arrow** — runs **up to the diamond "Is k <> 0?"**, rejoining the flow immediately above it. **Where the back-arrow attaches and why.** It attaches to the **diamond**, not to the first READ box and not to `total = 0`. `WHILE` is a **pre-test** loop: the condition must be evaluated before every pass, including the first, and the body must be able to be skipped entirely if the first value read is already 0. Returning to the diamond gives exactly that — the condition is checked, the body runs, and the flow comes straight back to the condition. Returning to `total = 0` instead would reset the running total on every pass and the chart would print the last value rather than the sum; returning to the first READ box would make that box part of the loop and leave the diamond with a second entry from above that is never used. **Why READ k appears twice.** The loop's condition tests `k`, so `k` must already hold a value the *first* time the diamond is reached — hence the **priming read** before the diamond. Thereafter, each pass must refresh `k` before the condition is tested again — hence the **read at the end of the body**, whose flowline is the back-arrow to the diamond. Two boxes, one algorithm: the pseudocode has the same duplication, `READ k` once before `WHILE` and once as the last line of the body. **If it is drawn only once, inside the loop**, then the diamond is reached before any value has been read, so `k` is undefined at the first test and the chart is untraceable — and if `k` is assumed to start at 0 the condition `k <> 0` is false immediately, the body never runs, and the chart prints 0 for every input. **If it is drawn only once, before the loop**, the sentinel is worse: `k` keeps its first value for ever, so if that value is non-zero the condition stays true, the back-arrow is taken on every pass, the No branch is never reached and the STOP is unreachable — an infinite loop that adds the same number to the total for ever.
