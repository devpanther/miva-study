**1.** The slides state: *"A variable definition is also a declaration, but not all variable declarations are definitions."* What does this actually mean?

c) The programmer writes the declaration and the compiler creates the definition later, when it decides which memory address the variable will occupy
d) A declaration introduces a name and its type to the compiler; a definition does that **and** reserves the storage, so `extern int total;` declares `total` without defining it

**2.** *"Variable names are not stored inside the computer memory; the compiler replaces them with memory location addresses."* Which conclusion follows from that?

c) Because the name is discarded, the value stored in a variable cannot be read back once something else has been assigned to it
d) The compiler must build a table of names into the finished program so that the running program can look each variable up by name when it needs it

**3.** What does specifying a data type actually accomplish?
a) It restricts what the variable may be called, since each type permits a different set of names

c) It fixes the variable's value for the rest of the program, so that later statements cannot change it
d) It makes the program convert whatever the user types at the keyboard into the right form automatically

**4.** Beyond "one of them has a decimal point", what is the real difference between `int` and `float`?
a) An `int` lives in main memory while a `float` is held in the processor's floating-point registers
b) A `float` is a signed type and an `int` is unsigned, which is why `float` can hold negative values
c) An `int` holds a whole number exactly within a fixed range; a `float` holds an approximation of a real number to a fixed number of significant digits, so a value such as 0.1 is not stored exactly
d) A `float` can hold every value an `int` can hold and more besides, so declaring everything `float` removes a whole class of errors

**5.** `&&` and `&` are both listed by the course, in different categories. What separates them?
a) `&&` is the logical AND for integers and `&` the logical AND for floating-point values

c) `&&` is logical: it takes whole truth values, yields 1 or 0, and evaluates its right operand only if the left has not already settled the answer. `&` is bitwise: it combines the two operands bit by bit and always evaluates both
d) `&` is only ever the address-of operator, so the bitwise AND has to be written `&&`, which is why the two look alike

**6.** Which list puts the operator categories in order from **highest** precedence to **lowest**?

**7.** Precedence and associativity are two different rules. Which statement gets both right?

## Answers

**1. d — A declaration introduces a name and its type; a definition also reserves the storage.** *Concept: declaration vs definition — storage is the dividing line.* The compiler needs two different things at two different moments. To *check* a statement such as `total = total + 1` it only needs to know that `total` exists and is an `int`; that is a **declaration**. To *build* the program it must also set aside bytes for `total` somewhere; that is a **definition**. Every definition therefore does the declaring job too, and the one-way implication in the slide falls out. `extern int total;` is the standard example of the other kind: it says "an `int` named `total` exists, defined elsewhere", and it reserves nothing. (a) is the commonest wrong answer and it confuses definition with **initialisation** — `int x;` is a complete definition, the storage exists, the bytes simply hold whatever was there before. (b) invents a scope rule; both file-level and block-level `int x;` are definitions. (c) inverts the roles: the compiler does assign the address, but it does so *because* the programmer wrote a definition — the compiler never manufactures storage for a name that was only declared.

**2. b.** *Concept: names are compile-time; addresses are run-time.* The name is a device for the human. Once the compiler has finished, every use of `total` has been turned into "the four bytes at such-and-such an address", and the identifier plays no further part. Hence the test in the answer: change `total` to `sum` everywhere consistently and recompile, and the machine code is the same program. (a) is the plausible-sounding inversion of the very statement being quoted — if the names *were* stored, long names would cost memory; because they are not, they cost nothing at run time. (d) describes a real thing (a debug symbol table) but gets its purpose backwards: it is added *for the debugger*, not so that the running program can find its own variables, and it is exactly what the quoted statement says the ordinary compiled program does not need. (c) confuses discarding the *name* with discarding the *value*; the bytes at the address are read as often as you like.

**3. b.** *Concept: what a type fixes — size, interpretation and legal operations.* The course's own wording is that data types **determine the type and size of the data associated with variables**. Size is the byte count reserved; type is the reading rule for those bytes; and the two together decide what can be done with them, which is why `%` is legal on two `int`s and illegal on a `float`. (c) confuses a type with the `const` qualifier — a type constrains what kind of value may be stored, never whether it may be stored again. (d) confuses declaring a type with input conversion: nothing about `int n;` makes `scanf` or the user behave; a mismatched conversion specifier simply produces rubbish. (a) inverts the relationship between the two halves of a definition — the naming rules in C are the same whatever the type is.

**4. c.** *Concept: exactness and range are separate properties.* `int` is exact but bounded; `float` trades exactness for range, keeping a sign, an exponent and a fixed number of significant digits, so most decimal fractions — 0.1 among them — are stored as the nearest representable value and not as themselves. That is why you count with `int` and measure with `float` or `double`. (d) is the trap, because its first clause is nearly true — a `float` really does reach far larger magnitudes than an `int` — but it is exactly the wrong conclusion: a 4-byte `float` cannot hold every 4-byte `int` exactly, because it spends bits on the exponent, and accumulating money or loop counters in `float` introduces error an `int` never has. (b) is invented: both are signed unless you write `unsigned`, and `unsigned` cannot be applied to `float` at all. (a) confuses where a value is stored while being worked on with what its type means; both types live in memory and both are loaded into registers to be operated on.

**5. c.** *Concept: logical vs bitwise, and short-circuit evaluation.* Two separate differences, and both are examinable. First, what they operate on: `&&` treats each operand as a single truth value (zero is false, anything else true) and yields 1 or 0, whereas `&` pairs the operands up bit by bit — which is why `1 & 2` is **0** (no bit is set in both) while `1 && 2` is **1** (both are non-zero). Second, evaluation: `&&` stops as soon as the left operand is false, so its right operand may never run; `&` is an arithmetic operator and always evaluates both. (a) invents a type-based split that does not exist; `&` is not defined on floating-point operands at all. (b) is the "they must be the same thing" guess, which the `1 & 2` case disposes of immediately. (d) picks up a real fact — `&` is also the address-of operator — and over-generalises it; which operator `&` is depends on whether it appears with one operand or two, and `&&` is never bitwise.

**6. c.** *Concept: the precedence ladder.* Unary operators bind tightest, then multiplicative, then additive, then the relational comparisons, then equality, then `&&`, then `||`, and assignment sits near the bottom. This order is not arbitrary: it is arranged so that ordinary expressions read the way mathematics reads them, and so that a condition such as `a + 1 < b * 2 && c != 0` needs no brackets at all — the arithmetic happens first, then the comparisons, then the logical joins, then any assignment. (b) is the exact reversal, and it comes from the belief that the operator you *want* done first should be highest, or from reading the standard's table upwards. (a) is the commonest genuine error: it puts the unary operators *below* the binary arithmetic, which would make `-a * b` mean `-(a * b)` — accidentally right — but `!a && b` mean `!(a && b)`, which is wrong. It also flattens equality and relational into one level, which they are not. (d) merges `*` with `+` (so `2 + 3 * 4` would be 20) and puts equality below the logical operators, which would make `a == b && c` mean `a == (b && c)`.

**7. a.** *Concept: precedence vs associativity — different levels vs the same level.* Precedence is a comparison between operators of **different** levels: `*` outranks `+`, so `2 + 3 * 4` is 14. Associativity is the tie-break when two operators sit at the **same** level: `/` and `*` are both multiplicative, so nothing in the precedence table settles `6 / 2 * 3`, and left-to-right associativity does — `(6 / 2) * 3` = 9, not `6 / (2 * 3)` = 1. Assignment and the unary operators are the ones that associate the other way, right to left, which is why `a = b = 0` means `a = (b = 0)` and why `!!x` is `!(!x)`. (d) is the widespread half-memory that "C goes left to right"; it is true of most levels and false of exactly the ones that matter most. (b) invents a category split that no table has. (c) swaps the two definitions round, which sounds fluent and is testable: it would leave `6 / 2 * 3` undecided, since both operators are at one level.

**8. b.** *Concept: structure vs union — the same syntax, different memory layout.* The course defines both with the *same* phrase, *a user-defined data type that can be used to group items of possibly different types into a single type*, and then gives the one difference that matters: **all of a union's members start at the same location in memory**, and **a union variable can represent the value of only one of its members at a time**. So the structure is 60 bytes with three independent strings; the union is 20 bytes, and writing `breed` writes over `name`. (a) is the trap for anyone who tried to find the difference in the definition wording rather than in the memory statement — "possibly different types" is said of **both**. (c) is false in both halves: both are user-defined, and both need their keyword (`struct Dog d;` / `union Dog d;`). (d) confuses union with **class**, which is the one that adds methods; a union has variables only.

**9.** *Concept: a data type as a size plus a reading rule.* The course's definition: **a data type is used for specifying the type of a variable; data types determine the type and size of the data associated with variables**, and **the three basic types in the C language are characters, integers and floating-point numbers** — `char`, `int` and `float` (with `double` as the wider floating type). What "type and size" means at run time: **size** is the number of bytes the definition causes to be reserved — typically 1 for `char`, 4 for `int`, 4 for `float`, 8 for `double` — and **type** is the rule for reading those bytes, because in memory there is nothing there but bits. Four bytes hold 32 bits and no more; read as a two's-complement integer they are one number, and read as an IEEE-754 floating-point value, where the leading bit is a sign, the next eight an exponent and the remaining twenty-three a mantissa, they are a completely different number. The same 32 bits are therefore both a perfectly good `int` and a perfectly good `float`, and **nothing in the bytes says which**. What decides is the **declared type of the variable**, which the compiler remembers and the running program does not need to: the compiler has already chosen the instructions — integer add or floating-point add, integer divide or floating-point divide — and baked them into the code. Three consequences worth stating. The size fixes the **range**, which is why an `int` overflows at about ±2.1 billion. The reading rule fixes **which operations are legal**, which is why `%` works on two `int`s and is rejected on a `float`. And the reading rule fixes **what an operation means**, which is why `7 / 2` is 3 with two `int`s and 3.5 with a floating operand — same symbol, different machine instruction.

**10.** *Concept: declaration, definition, initialisation, and the naming rules.* A **declaration** tells the compiler that a name exists and what type it has, so that uses of the name can be checked: `extern int total;`. A **definition** does that and additionally **reserves the storage**: `int total;` — the course's rule, **data type followed by variable name**. An **initialisation** is a definition that also supplies a starting value: `int total = 0;`. Every definition is a declaration; not every declaration is a definition; and a definition without an initialiser leaves the reserved bytes holding whatever was in them, which is *not* zero and *not* nothing. **Why the distinction is needed:** a real program is built from several source files compiled separately, and each file must be checkable on its own. If every mention of a name reserved storage, a variable shared between two files would be created twice — two different addresses, two different values, one name — and neither file could refer to the other's. The declaration is what lets file B say "there is an `int` called `total` and here is its type; the storage belongs to someone else", so the linker can join the reference to the one definition. The same split is what makes function prototypes work. **Naming rules in C:** a name is made of letters, digits and the underscore only; it may **not begin with a digit**; it may contain **no spaces or other punctuation**; it may **not be a keyword**; and it is **case-sensitive**, so `Total` and `total` are two variables. So: `2ndScore` breaks the rule that a name may not begin with a digit; `total score` breaks the no-spaces rule and would be read as two tokens; `float` breaks the no-keywords rule, since `float` is reserved to name a type; `unit-price` breaks the permitted-characters rule and would be read as `unit` minus `price`.

**11.** *Concept: state in variables, behaviour in methods, and encapsulation as the mechanism behind every benefit.* **Real-world objects have two main characteristics: state and behaviour.** The course's dog has the state *name, colour, breed, hungry* and the behaviour *barking, fetching, wagging its tail*. In a programme object the mapping is exact: **the state of an object is stored in variables and the behaviour of objects is described by methods**, and **every object has its own variables and methods** — two dog objects have two separate `name` variables, not one shared between them. The restriction is the interesting part. **Only the methods of a particular object have access to the variables of that object**, and **different objects can only interact with each other through their own individual methods**. So the variables are not reachable from outside; the only doors into an object's state are the methods it publishes, which is what the access specifiers `private` and `public` control, and what **data encapsulation** names — *hiding the implementation details of an object from the user, so the user can only interact with the object through a set of public methods while the internal workings remain hidden*. Now the mechanism behind each claimed benefit. **Independent creation and maintenance:** because no outside code touches the variables, nothing outside can be depending on how they are arranged; the internals can be rewritten — a different representation, an extra field, a faster algorithm — and every user of the object still compiles and still works, provided the methods keep their signatures. That is what makes the object *independent* rather than merely *separate*. **Reuse in various parts of the programme:** the object carries its own state with it, so it does not rely on any particular surrounding context; dropping it into a second part of the programme needs no shared global to be set up first. **Removal and replacement — "similar to how a car works":** a faulty part can be swapped for another with the same fittings without rebuilding the car, and the fittings here are the method signatures; a misbehaving object can be **removed and replaced without creating problems for the rest of the code** precisely because the rest of the code only ever spoke to it through those methods. **Information hiding:** since the state is reachable only through methods, the author chooses which methods exist, and therefore **controls the amount of information shared about the object with the outside world** — a `get_name()` with no matching setter makes the name readable and unchangeable, which no arrangement of loose variables can enforce. Every one of the four rests on the same single fact: the variables are private and the methods are the only route to them.

**12.** *Concept: structure, union and class — what each holds and how it is laid out.* A **structure** is *a user-defined data type that can be used to group items of possibly different types into a single type*, defined with the `struct` keyword, its members reached with the **dot syntax** (`d.name`). It holds **variables only**. Its members each get **their own storage**, laid out one after another, so all of them hold values simultaneously and the size of the structure is the sum of its members' sizes (plus any padding the machine needs for alignment). A **union** is *defined in the same way* and holds **variables only** as well, with the `union` keyword and the same dot syntax; the difference is entirely in the layout — **all of its members start at the same location in memory**, overlapping completely, so **a union variable can represent the value of only one of its members at a time** and its size is the size of its **largest** member. A **class** is *similar to a structure, but in addition to having variables it also usually has methods or functions* — the dog class has `name`, `breed` and `colour` and also `get_name()` — and it adds **access specifiers** (`public`, `private`) that say who may reach which members, which is what makes encapsulation enforceable rather than merely conventional. **Sizes for the three given members.** Each is `char[20]`, so each is 20 bytes and `char` needs no alignment padding. `sizeof(struct Dog)` = 20 + 20 + 20 = **60 bytes**, because the three arrays sit at three different offsets. `sizeof(union Dog)` = **20 bytes**, because all three arrays start at offset 0 and occupy the same 20 bytes; the union must be big enough for its largest member and no bigger. **What the union buys, and the price.** It buys memory: where a value is known to be one of several alternatives and never more than one at a time — a token that is either an integer or a floating-point number or a string, say — the union stores it in the space of the largest alternative rather than the space of all of them added up, which matters in the small-memory settings C is used in. The price is that the type system no longer keeps track of which alternative is live: writing one member silently destroys the others, and reading a member that was not the last one written gives you the previous member's bytes reinterpreted, which is meaningless rather than merely wrong. The programmer must therefore carry that knowledge separately — conventionally by wrapping the union in a **structure** together with a small "tag" variable recording which member is currently valid, and checking the tag before every read.
