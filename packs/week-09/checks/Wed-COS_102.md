## Answers

**1. b — `if (2 - 2)`.** *Concept: truth in C is "not zero"; falsity is "exactly zero".* The course's rule is that **Boolean values are returned as integers with 1 (or any other number that is not 0) representing true and 0 representing false**. `2 - 2` evaluates to **0**, which is the one value that is false. (a) `-3` is not 0, so it is true — a negative number is just as true as a positive one, and the belief that "true means positive" is the commonest form of the error. (c) `'a'` is a character constant whose value is 97, which is not 0, so it is true. (d) `0.5` is not 0, so it is true; the trap here is thinking that a value "between false and true" must round down to false, when the only test performed is a comparison with zero. Note that none of the four contains a relational operator, and all four are still perfectly ordinary conditions — a condition does not need `==` or `<` to have a truth value.

**2. c.** *Concept: the "one statement" property is a syntactic fact, and it is what makes braces load-bearing.* Constructs such as `if`, `while` and `for` are defined to govern exactly **one** statement. A block is treated like a single statement, so wrapping several statements in curly brackets is the only way to put more than one of them under a condition or inside a loop — which is why the course lists the applications of blocks as **functions, decision making statements, and iterative statements**. (a) reads "treated like a single statement" as *atomic* or *uninterruptible*, importing an idea from concurrency that the course never raises; the statements inside a block run one after another exactly as they would anywhere else. (b) reads it as a performance claim; the block compiles to the same instructions as the statements alone and grouping is not an optimisation. (d) invents a shared semicolon; each statement inside the block keeps its own, and the reason **the right curly bracket does not have a semicolon after it** is that the brace itself closes the block.

**3. d — `!a && !b`.** *Concept: De Morgan — pushing a `!` inside brackets flips the operator as well as negating each operand.* "Not (a or b)" means "neither" — both must be false — which is `!a && !b`. (a) negates the operands but leaves the operator, giving `!a || !b`, which is the law for `!(a && b)`; the two laws are commonly memorised as one and then applied to the wrong expression. Check `a = 1, b = 0`: `!(1 || 0)` is 0, but `!1 || !0` is `0 || 1` = 1. (b) drops the negation and swaps the operator arbitrarily; it agrees with the original only when both are false. (c) negates one operand only, which cannot be right by symmetry — `a` and `b` play the same role in `a || b`, so they must play the same role in its negation.

**4. a.** *Concept: `&&` binds tighter than `||`, exactly as `*` binds tighter than `+`.* Equality forms first (`a == 0`, `b == 0`, `c == 0`), then `&&` joins the last two, then `||` joins that result to the first. So the expression is true if `a` is 0, **or** if `b` and `c` are both 0. (b) is the reading of someone who takes `||` and `&&` to be equal in precedence and left-associative, which would make the expression true only when `c` is 0 — a completely different condition, and the fault that produces "my check works except when *c* is nonzero". (c) treats `==` as though it bound loosest and chains it, which is not how any of these operators associate. (d) invents a duplicated operand. The safe habit, and the one the exam rewards, is to write the brackets in (a) explicitly even though they are not required.

**5. c.** *Concept: short-circuit evaluation — a skipped operand is not evaluated, so its side effects do not happen.* `&&` evaluates its left operand first; `check(x)` returns 0, which is false, and no value of the right operand can make `0 && anything` come out as anything but 0. So the answer is settled, `record(x)` is **never called**, nothing is written to the file, and the expression is 0. (a) is the misconception that `&&` is like arithmetic and must collect both operands before combining them; if that were so, the standard guard `if (n != 0 && total / n > 5)` would divide by zero. (d) invents a default value for an unevaluated operand; there is no value, because there was no evaluation — the result comes entirely from the left operand. (b) invents a restriction on what may appear in a condition; function calls with effects are legal there, which is precisely why the skipping rule has to be known rather than assumed.

**6. c.** *Concept: `while` tests before the body, `do-while` after; only `do-while` is guaranteed to run at least once.* The course states it directly: a **`do-while` loop works the same way as a `while` loop, except the fact that it is guaranteed to execute at least one time.** With a condition that is false from the start, a `while` evaluates it, finds 0, and passes control to the line immediately following the loop without entering the body; a `do-while` executes the body first and only then discovers the condition is false, so exactly one pass has happened. (a) has both rules the right way round in the words and the wrong way round on the constructs — the classic swap, and the reason the answer must be reasoned from *where the test sits* rather than recalled as a pair of labels. (b) applies the `while` rule to both, which would make `do-while` pointless as a separate construct. (d) applies the `do-while` rule to both, which would make a zero-pass `while` impossible and would break every loop written to handle an empty list.

**7. b.** *Concept: an `if-else-if` chain stops at the first true condition; separate `if`s test every condition independently.* In the chain, `n = 200` satisfies `n > 100`, so `A` runs and **`n > 50` is never even tested** — every later condition is skipped. Rewritten as three separate `if`s, all three conditions are evaluated: `200 > 100` is true so `A` runs, `200 > 50` is also true so `B` runs, and the third `if` (whatever bare condition replaced the `else`) runs `C` as well if it is true. The chain's later branches are written on the assumption that all earlier conditions failed, and separating them destroys that assumption silently. (a) is the belief that the same conditions must give the same behaviour; what differs is not the conditions but which of them are **reached**. (c) treats the difference as efficiency only, which is the half-right answer that costs the mark: the early stop is not merely faster, it is what makes the branches exclusive. (d) is wrong about `else` — a final `else` can be replaced by an `if` carrying the negation of the earlier conditions, so `C` is still reachable; it is simply no longer automatic.

**8. a.** *Concept: the course's definitions of the two kinds of branching.* Word for word: with unconditional branching **some unconditional statements can move program control to either a specific statement or block without checking any condition**, and the example given is **`goto`**; with conditional branching **where program control moves to is dependent on if some predetermined conditions are satisfied or not**, and such statements **are also known as decision making or selection statements**. (b) inverts the definition of branching itself: the course says **branching means that the computer can decide to move program control to another line of code instead of the usual movement from one line to the next line** — the ordinary sequential flow is what branching departs from, not a kind of branching. (c) misassigns the constructs; loops are **iterative** statements, and `goto` — not the loop — is the deck's example of an unconditional branch. (d) invents a compile-time/run-time distinction; `goto` transfers control while the programme runs, and both kinds of branching are run-time behaviour.

**9.** *Concept: a Boolean expression is an expression with an integer value, and both `=` and `== true` fail because of what that value is.* **What a Boolean expression is.** It is an expression whose purpose is to be true or false: typically a comparison of values or variables — the course's point that **to make decisions and find answers in programming it is sometimes useful to compare values and variables, and when this comparison activity takes place the return value is usually a Boolean value** — combined where necessary with `&&`, `||` and `!`. The six relational operators are `==`, `!=`, `<`, `>`, `<=`, `>=`. **What it evaluates to.** Not a question and not a special kind of thing: an ordinary **integer**. The course's rule is that **Boolean values are returned as integers, with 1 (or any other number that is not 0) representing true and 0 representing false.** So `7 > 3` has the value 1 exactly as `3 + 4` has the value 7; it can be printed with `%d`, stored in an `int`, or added to another. An `if` does one thing only: it evaluates its expression and asks whether the result is zero. **Fault 1: `if (x = 5)`.** `=` is the **assignment** operator, not the comparison operator. `x = 5` stores 5 in `x`, and the value of the assignment expression is the value assigned, namely 5. Five is not zero, so the condition is **true**, and it is true regardless of what `x` held before, because the old value was overwritten before anything was tested. Two things go wrong at once: the branch always runs, and the variable is silently destroyed. It compiles without complaint because an assignment is a perfectly legal expression. *Should have been written:* `if (x == 5)`. **Fault 2: `if (flag == true)`.** `true` is the name `<stdbool.h>` gives to the integer **1**, so this expression compares `flag` with 1 — nothing more. If `flag` holds 2, then `flag == true` is `2 == 1`, which is **0**, so the branch is skipped, even though 2 is a perfectly good true value by the course's own rule. The test has quietly narrowed "true" from "not zero" to "exactly one". *Should have been written:* `if (flag)`, which applies the actual rule; and for the negation, `if (!flag)` rather than `if (flag == false)`. The general principle behind both faults: an `if` never compares anything with truth — it compares with zero — so the condition should be written to *be* the truth, not to be tested against it.

**10.** *Concept: the truth tables, De Morgan's laws, and why C has no chained comparison.* **The tables**, in C's own values:

| `a` | `b` | `a && b` | `a \|\| b` | `!a` |
|---|---|---|---|---|
| 0 | 0 | 0 | 0 | 1 |
| 0 | 1 | 0 | 1 | 1 |
| 1 | 0 | 0 | 1 | 0 |
| 1 | 1 | 1 | 1 | 0 |

**The rules in one sentence each.** `&&` is true **only when both** operands are true, so a single false operand settles the result. `||` is false **only when both** operands are false, so a single true operand settles the result. `!` **swaps** 1 and 0. (Notice that the "single operand settles it" phrasing is the same fact as short-circuit evaluation, seen from the table rather than from the evaluation order.) **De Morgan's laws.** `!(a && b)` is `!a || !b` — *not both* means *at least one is not*. `!(a || b)` is `!a && !b` — *not either* means *neither*. In both, the **operator flips as well as the operands**; that flip is the whole content of the law and it is what students drop. **The disproof of the wrong form.** Take the row `a = 0, b = 1`. Then `a && b` is 0, so `!(a && b)` is **1**. But `!a` is 1 and `!b` is 0, so `!a && !b` is `1 && 0` = **0**. They disagree on that row, so `!(a && b)` is not `!a && !b`; the correct right-hand side is `!a || !b`. (By symmetry they also disagree on `a = 1, b = 0`; they agree only on the two rows where `a` and `b` happen to be equal, which is why testing on tidy sample data does not expose the mistake.) **Why `0 < x < 10` is always true.** Relational operators associate **left to right**, and C has no chained comparison, so the expression means `(0 < x) < 10`. The inner comparison is evaluated first and — by the integer rule — yields **1** or **0**. That integer is then compared with 10, and both 1 and 0 are less than 10, so the whole expression evaluates to **1** for every possible value of `x`, including `x = -500`. The result does not depend on `x` at all, which is what makes the bug total rather than occasional. **What must be written instead:** `0 < x && x < 10`, i.e. two complete comparisons joined by `&&`. Each operand of `&&` must be a full Boolean expression in its own right; a range test cannot be written by leaving one side of a comparison implicit. The same applies to `if (x == 1 || 2)`, which means `(x == 1) || 2` and is always true because 2 is nonzero — it must be `x == 1 || x == 2`.

**11.** *Concept: precedence order, and short-circuiting as a rule about evaluation rather than about speed.* **Precedence, highest first:** `!` (unary), then `*`, then `+`, then `<` (with `<=`, `>`, `>=`), then `==` (with `!=`), then `&&`, then `||`, then `=` last of all. Two features of the list are examined repeatedly: **`!` binds tighter than every comparison**, and **relational binds tighter than equality**, which binds tighter than `&&`, which binds tighter than `||`. Assignment is not a special form but an operator, and the lowest-precedence one here, which is why `x = a > b` assigns the *comparison's* value to `x`. **Bracketing the expression.** `x + 1 > y * 2 && !flag == 0` becomes:

```c
((x + 1) > (y * 2)) && ((!flag) == 0)
```

Arithmetic forms first, giving `x + 1` and `y * 2`; `!` forms next, giving `!flag`; then `>` and `==` produce two truth values; then `&&` joins them. Worth noting what the right-hand half actually says: `(!flag) == 0` is true exactly when `!flag` is 0, i.e. exactly when `flag` is true — so the whole clause is a long-winded way of writing `flag`, and anyone who read it as `!(flag == 0)` has arrived at the same meaning by an argument that is wrong and will fail on the next example. **What short-circuiting guarantees.** For `a && b`: `a` is evaluated first, and **if `a` is false, `b` is not evaluated at all**, since the result is already 0. For `a || b`: `a` is evaluated first, and **if `a` is true, `b` is not evaluated**, since the result is already 1. This is a guarantee of the language about *what gets evaluated*, not a permission the compiler may or may not take up. **Why operand order is meaning, not style.** Because a skipped operand is never evaluated, **its side effects never happen** and any error it would have raised never occurs. So `if (n != 0 && total / n > 5)` is safe for `n == 0` — the division is unreachable — while `if (total / n > 5 && n != 0)` performs the division first and divides by zero. The two have identical truth tables and different behaviour, which is only possible because evaluation is ordered. The same logic applies to increments: in `i++ > 0 && j++ > 0`, `j` is left untouched whenever the left operand is false, so the values of the variables after the statement depend on which operand was written first. The working rule is: **guard on the left, guarded expression on the right**, and never hide an assignment, an increment or a call with an effect in the right-hand operand. **If `&&` is replaced by `&`.** `&` is the **bitwise** and, a different operator: it combines the operands bit by bit and — critically — **always evaluates both of them**. The guard is therefore gone, and `if (n != 0 & total / n > 5)` divides by zero. It also gives different answers, because it works on bits rather than truths: `2 && 1` is 1, but `2 & 1` is 0. The single-character typo is invisible on the page and changes both what is computed and what is executed.

**12.** *Concept: the entry condition and pass count of every control construct in the week.* **`if (c) S`** — control enters `S` **only if `c` is true**; the course's words are that **program control will only move inside the `if` block if some conditions are satisfied, or else the entire block will be skipped.** Body runs **minimum 0, maximum 1** times. **`if (c) S else T`** — **if the condition is satisfied program control moves inside the `if` block, otherwise it moves to the `else` statement block.** Exactly **one** of the two runs, always: minimum 1, maximum 1 branch taken. There is no path on which both run and none on which neither runs. **`if-else-if`** — used when **more than two choices are integrated into the decision making process**. Conditions are tested **top to bottom** and the **first true one wins**; its branch runs and every remaining condition is skipped untested. At most **one** branch runs; if the chain has no final bare `else` and no condition is true, **none** runs. Each condition after the first is therefore read in the context of all the earlier ones having failed. **`switch`** — **we can execute one code block among many alternatives**. The controlling expression is evaluated, control **jumps** to the matching `case` label, or to `default` if no label matches (and out of the `switch` entirely if there is no match and no `default`). **After a matching case finishes with no `break`, control does not leave the `switch`: it falls straight through into the statements of the following case, and continues doing so until it meets a `break` or the closing brace.** So a missing `break` changes which code runs, and is not a formatting matter. **`while (c) S`** — the condition is tested **before** the body; **the loop iterates while the condition is true, and when the condition becomes false, program control passes to the line immediately following the loop.** Body runs **minimum 0**, maximum unbounded. **`do S while (c);`** — the body runs first and the condition is tested **after** it, so it is **guaranteed to execute at least one time**: minimum **1**, maximum unbounded. **`for (init; c; inc) S`** — **the init step is executed first, and only once**; then the condition is evaluated, and **if it is true the body executes, if it is false the body does not execute**. After each pass the **increment** runs, and only then is the condition tested again. So the order per pass is condition, body, increment, condition — the increment happens **after** the body and **before** the next test, which is why the control variable holds the first *failing* value once the loop has ended. Body runs **minimum 0**, maximum unbounded. **`goto`** — unconditional: control moves **without checking any condition at all**, so there is no entry condition to state. **Why `if-else` and two separate `if`s are not interchangeable.** With `if (c) S else T`, `T` runs precisely when `c` is false, and the two branches are mutually exclusive by construction — `c` is evaluated **once**. With `if (c) S` followed by `if (d) T`, both conditions are evaluated independently, so if `c` and `d` are both true **both** bodies run. Writing `if (c) S` then `if (!c) T` restores exclusivity but evaluates `c` twice, which differs if evaluating `c` has a side effect or if something between the two statements changes the value `c` depends on. The `else` is not shorthand for a second test; it is the guarantee that no second test is made.
