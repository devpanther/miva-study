*Algorithm concepts only: what an algorithm is as against a program and a computer, the five characteristics, the five development steps, how algorithms are represented, the three control structures as representation requirements, design considerations, and priori/posterior analysis with the complexity vocabulary. No tracing or debugging tonight.*
*Sit cold, notes closed, about 15 minutes. Score out of 12.*

**1.** A student writes numbered English steps for computing a class average, types those steps into a Python file, and runs the file on her laptop. Which names all three correctly?
a) The English steps are the algorithm, the Python file is the program, the laptop is the tool
b) The English steps are the program, the Python file is the algorithm, the laptop supplies the plan
c) The English steps are notes, the Python file is the algorithm, the run is the program
d) All three are the algorithm at different stages, since the logic is the same throughout

**2.** Two students implement one agreed plan, one in C and one in Java; the outputs are identical. A third student says these are two different algorithms because the code differs. Which characteristic settles it?
a) Finiteness — each program has a limited and countable number of instructions
b) Effectiveness — each program produces output, so each is an effective version
c) Language independence — the algorithm does not depend on any programming language
d) Unambiguity — clear instructions can be written in any language without change

**3.** A written procedure contains "Step 3: add a suitable quantity of reagent" and "Step 4: set p to the largest prime number". Which characteristic does each step violate?
a) Step 3 violates effectiveness; Step 4 violates unambiguity
b) Step 3 violates unambiguity; Step 4 violates effectiveness
c) Both violate finiteness, since neither step can be completed
d) Step 3 violates input; Step 4 violates language independence

**4.** A team writes down: "What data do we have? Where is the data? What formulas are related to the problem?" This belongs to:
a) Step 1, checking the description for incompleteness
b) Step 2, deciding the starting point
c) Step 2, deciding the ending point
d) Step 3, choosing the main parts of the solution

**5.** Working from the high-level meeting algorithm, a team expands "find common empty spaces in calendars" into four sub-steps, and also adds a new final step, "book a projector". Which is correct?
a) Both are refinement, since both add detail that the high-level version omitted
b) Neither is refinement; refinement only fixes variable names once a language is chosen
c) Only the projector step is refinement, since it supplies a detail left out earlier
d) The calendar expansion is refinement; the projector step alters the plan itself

**6.** The course requires that an algorithm be represented with sequence, selection and repetition. The stated reason is:
a) So that it is easily translatable into various programming languages
b) So that it consists of inputs, a process and outputs
c) So that its time and space complexity can be computed
d) So that it can be drawn as a flowchart rather than as pseudocode

**7.** Team A counts on paper how many times an inner statement runs for n items, before any code exists. Team B compiles the Java version and records its memory use and running time. Which is correct?
a) A is priori and B is posterior, since posterior follows implementation and covers space and time
b) A is posterior and B is priori, since measurement precedes design in the course's ordering
c) Both are posterior, because both are concerned with the efficiency of the algorithm
d) Both are priori, since neither of them directly affects the implementation of the algorithm

**8.** Three loops: **L1** adds 3 to `i` each pass until `i > n`; **L2** halves `i` each pass until `i < 1`; **L3** is a pair of nested loops whose inner statement runs n times for each of n outer passes. Their time complexities are:
a) L1 O(n), L2 O(log n), L3 O(n²)
b) L1 O(3n), L2 O(log n), L3 O(n²)
c) L1 O(log n), L2 O(n), L3 O(n²)
d) L1 O(n), L2 O(log log n), L3 O(2ⁿ)

**9. (explain why)** A student argues that a set of instructions satisfies finiteness "as long as you can count the instructions, which you always can". Explain what finiteness actually requires, why counting the written lines is not enough, and how finiteness differs from effectiveness. Give one procedure that has few clear instructions yet fails finiteness, and one that is finite and unambiguous yet fails effectiveness.

**10. (explain why)** One algorithm is written three times: as a flowchart, as pseudocode, and as numbered English steps. State what differs between the three versions and what cannot differ. Then explain why the course insists on pseudocode or flowchart rather than leaving the algorithm in the client's own prose, referring to the three issues it names at the problem-description step.

**11. (explain why)** The course says that "writing the same step on different lines is not sustainable", and therefore introduces repetition. Explain what repetition buys beyond shorter text — that is, what an algorithm written with sequence alone can and cannot do — and state what selection adds that neither sequence nor repetition supplies.

**12. (explain why)** A payroll algorithm produces the right figures on every test the team ran, but its behaviour is undefined when the employee list is empty, and it is written as one unbroken block of 200 steps with no separable parts. ## Answers

**1. a** — *Algorithm vs program vs computer.* The course states the three separately: an **algorithm is a plan for solving a problem, designed by people**; a **program is the set of instructions describing the steps the computer has to follow**; a **computer is a tool used to carry out a problem-solving plan**. The English steps are the plan, the Python file is the plan converted into a program, and the laptop is the tool. (b) inverts plan and program and credits the machine with the plan, which is exactly what the course denies. (c) comes from thinking that only *code* can be an algorithm, so the English version gets demoted to "notes" — but the algorithm is language-independent and exists before any code. (d) is the subtlest error: the logic really is the same throughout, but the course distinguishes the three by their **role** (plan, instructions, tool), not by their logic, and it says the algorithm **must be converted into** a program — a conversion between two different things.

**2. c** — *Language independence.* The course lists it as a characteristic: algorithms **should not be dependent on any programming language**. One plan implemented twice is one algorithm and two programs. (a) is true of both programs and settles nothing — finiteness is about the number of instructions, not about which language they are in. (b) misreads effectiveness as "it produced output"; effectiveness is about each step being carryable-out and the algorithm doing the job, and it too would be satisfied by both, so it cannot decide the question. (d) is the near-miss: unambiguity is what makes an algorithm *implementable* by a reader, but it is language independence that says the identity of the algorithm survives the change of language.

**3. b** — *Unambiguity vs effectiveness.* "A suitable quantity" has more than one reading, so the instruction is not **straightforward and clear**: it fails **unambiguity**. "The largest prime number" is perfectly clear — every reader understands it identically — but there is no largest prime, so the step **cannot be carried out**: it fails **effectiveness**. (a) is the same pair swapped, and it is the answer of anyone who has learned both words but attached them to the wrong test ("clear" vs "doable"). (c) is the common conflation of "cannot be completed" with **finiteness**; finiteness is about a **limited and countable number of instructions** and the algorithm ending, not about one step being impossible. (d) attaches characteristics with no bearing: neither step concerns input values, and neither mentions a programming language.

**4. b** — *Problem analysis: starting point.* The course splits Step 2 into questions that fix the **starting point** — what data do we have, where is it, what formulas relate to the problem, what rules manipulate the data, how are the values related — and questions that fix the **ending point**. All three quoted questions are from the starting-point list. (c) is the discriminating distractor: it names the right step but the wrong half, which is precisely the split the course draws. The ending-point questions ask what results are expected, what parameters changed, what changes were made, what items are now non-existent. (a) confuses analysis with description, which is the step *before*; (d) confuses it with high-level development, the step *after*.

**5. d** — *Refinement adds detail to a step, not stages to the plan.* Step 4 is **stepwise refinement**: providing more detail about each high-level step, based on who will implement it, their knowledge, and the computer specifications. The course's own example refines "find common empty spaces in calendars" into ask/examine/find/iterate — one step becoming four sub-steps of the same step. Booking a projector is a new activity the plan did not contain, so it revises the high-level algorithm (or exposes an incomplete description) rather than refining it. (a) is the answer of anyone who treats "more detail" as the whole test, ignoring that refinement is refinement **of a step**. (b) confuses refinement with implementation, but refinement happens before any language is chosen. (c) has the distinction backwards.

**6. a** — *Why sequence, selection and repetition are required.* The course states it directly: it is important to present algorithms in ways that make them **easily translatable into various programming languages**, and to achieve this the representation should have sequence, selection and repetition. (b) quotes a true statement about an algorithm's makeup — inputs, a process and outputs — which is a different sentence in the same lecture and is not a property of the representation. (c) attaches the requirement to complexity analysis, which is Algorithms II material and does not depend on how the algorithm is written down. (d) mistakes a requirement common to **both** representations for a reason to prefer one over the other.

**7. a** — *Priori vs posterior analysis.* **Priori analysis is carried out before implementing an algorithm in a particular programming language and does not directly affect the implementation**; **posterior analysis is carried out after implementation and deals with the space and running time requirements**. Counting iterations on paper before any code is priori; measuring the compiled Java program's memory and time is posterior by definition. (b) simply inverts the two. (c) comes from equating "efficiency" with posterior analysis — but priori analysis is efficiency reasoning too, done in advance. (d) misreads "does not directly affect the implementation" as though it were a test that both activities pass; the operative word in the definitions is **before** versus **after** implementation.

**8. a** — *Reading complexity classes off loop behaviour.* The course's rules: a loop is **O(n)** if the loop variable is **incremented or decremented by a constant amount** (L1 adds 3, a constant); **O(log n)** if the loop variable is **divided or multiplied by a constant amount** (L2 halves); and for **nested loops** the complexity is **the number of times the innermost statement is executed**, here n × n, so **O(n²)**. (b) keeps the constant and writes O(3n) — big O describes the **growth rate**, which the multiplier 3 does not change. (c) swaps the increment rule with the division rule, the error of remembering "the variable changes by a constant" without noticing which operation. (d) makes two separate mistakes worth naming: **O(log log n)** is the rule for a loop variable **reduced or increased exponentially**, not halved, and **O(2ⁿ)** is the rule for recursion that solves two subproblems of size n−1, not for two nested loops.

**9.** *Concept: finiteness in execution vs effectiveness.* **Finiteness** in the course's sense is that an algorithm has a **limited and countable number of instructions** *and* comes to an end: the instructions are finite in number and the execution is finite in length. Counting the written lines only settles the first half. A four-line procedure that says "set `i` to 1; while `i` is less than 10, print `i`; end while; stop" has four countable instructions and never terminates, because nothing changes `i` — the text is finite, the execution is not, and it is the execution that the characteristic is about. **Effectiveness** is a different demand: each step must be one that can **actually be carried out**, and the steps together must do the job. The two come apart in both directions. *Few clear instructions, fails finiteness:* the loop just given, or "keep adding 1 to n and print the result" — every step is doable and unambiguous, and the procedure never ends. *Finite and unambiguous, fails effectiveness:* "Step 1: set p to the largest prime number; Step 2: print p" — two instructions, one reading, and Step 1 cannot be performed by anyone, so nothing is ever printed. The practical mark of the difference is where you look: finiteness is judged by watching the algorithm run to its end, effectiveness by asking of each step whether it is a thing a person or machine can do.

**10.** *Concept: representation vs algorithm; why a controlled notation.* What differs between the three versions is only the **notation**: the flowchart carries the logic in symbols (oval start/stop, parallelogram input/output, rectangle process, diamond decision, arrows for flow), pseudocode carries it in structured text with `IF`/`WHILE`/`INPUT`/`OUTPUT` keywords, and numbered English steps carry it in prose. What cannot differ is the algorithm itself: the **order of the steps**, the **inputs, process and outputs**, the decisions taken and the repetitions performed, and hence the result produced on any given input, and the complexity. Choosing a representation never makes an algorithm faster or more correct; it is the same plan wearing different clothes, which is why the course can say algorithms "can be represented as **either** pseudocodes **or** flowcharts". The reason for insisting on one of those two rather than the client's own prose is the three faults the course names at the problem-description step. Ordinary prose invites **unstated assumptions** ("print the report in the usual format" — the format is in the client's head, not on the page); it invites **ambiguity**, because sentences that read as one instruction to the client read as two or as none to the programmer; and it invites **incompleteness**, because prose has no slot that visibly stands empty. Pseudocode and flowcharts constrain the writer to make the **sequence** explicit, to state a **condition** for every selection, and to state a termination condition for every repetition — so an omission shows up as a missing branch or a loop with no exit, rather than hiding inside a fluent sentence.

**11.** *Concept: what repetition and selection add to sequence.* The course's argument is that when the same steps must be executed repeatedly, **writing the same step on different lines is not sustainable**, so a construct — `while condition is true do perform activity` — is used instead. But the gain is not merely brevity. Writing a step out five times fixes the number of repetitions **at the moment the algorithm is written**; a `WHILE` fixes it **at the moment the algorithm runs**, from the condition and hence from the data. That is the real purchase: an algorithm with sequence alone can only do a **fixed** amount of work, so it can be correct for one particular input size and no other. "Read a number, read a number, read a number, add them, print" is a correct algorithm for exactly three numbers and is simply wrong for four; the loop version handles any quantity, which is what makes the algorithm general enough to be worth reviewing at Step 5 ("can it be applied to more general problems?"). Sequence also gives no way for the work done to depend on the value of the data — every step happens on every run. **Selection** supplies exactly that: some steps are **selectively executed if some conditions are satisfied**, in either the one-branch form (`If condition is true Then perform activity`) or the two-branch form with an `else`, and the alternative steps executed may be one or more. Without selection there is no way to treat an invalid input differently from a valid one, and there is no way to end a loop meaningfully either, since a loop's continuation is itself a condition being tested. So: sequence fixes the order, repetition makes the **amount** of work depend on the data, and selection makes the **choice** of work depend on the data.

**12.** *Concept: design considerations, and why testing does not establish them.* The course's design considerations are that algorithms should be **modular** (breakable into smaller steps), **correct**, **maintainable and easily refactored**, **logical and practical**, **extensible** (another designer can update and upgrade it), **robust** (the solution to the problem is **clearly defined**), and **simple** (very easy to understand); the Summary sheet's list adds **functionality**. This payroll algorithm satisfies **correctness** on the inputs tried, and presumably its steps are logical and practical since they produce right figures. It fails **robustness**: the empty employee list has no defined behaviour, so the solution is not clearly defined over the whole range of inputs the problem admits. It fails **modularity**, because a single unbroken block of 200 steps cannot be broken into smaller steps — and that failure drags down **maintainability**, **extensibility** and **simplicity** with it, since a block that cannot be separated cannot be refactored, upgraded by another designer, or easily understood. Passing every test cannot establish these because a test exercises **one execution on one input**. Robustness is a claim about the inputs that were **not** tried, and the empty list is exactly such an input — a test suite that never supplies it reports nothing about it, so its silence is not evidence. Modularity, maintainability, extensibility and simplicity are not claims about executions at all: they are properties of the algorithm's **structure**, and the structure is unchanged by how often the algorithm is run correctly. This is why review (Step 5) asks whether the algorithm generalises and whether its complexity can be reduced, rather than merely whether it worked — those are questions testing cannot answer.
