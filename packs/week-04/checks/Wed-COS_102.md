# Wednesday — COS_102 nightly check

*What an algorithm is and how it differs from a program, the five development steps and what fails at each, the three forms of representation (sequence, selection, repetition), the characteristics and design considerations, and priori versus posterior analysis and complexity.*
*Sit cold, notes closed, 8 minutes. Score out of 6.*

**1.** Two programmers implement the same written procedure on identical input and get different answers. The procedure reads: "Step 1: accept the list of marks. Step 2: discard the marks that are clearly outliers. Step 3: compute the mean of the remainder. Step 4: output the mean." Which characteristic of an algorithm does this procedure fail?
a) Finiteness — the procedure contains no loop, so the number of instructions it will execute is not limited and countable
b) Unambiguity — an algorithm should have straightforward and clear instructions, and "clearly outliers" does not determine the same steps for two implementers, so the same input does not determine the same output
c) Language independence — the steps are written in English rather than in a programming language, which is why the two implementations diverged
d) Input — the procedure accepts a list of marks but never states how many marks there will be, so it has no properly defined input

**2.** A client asks for "a program that sorts our staff records". The programmer delivers one that sorts by surname; the client meant by department and then by salary within department. Which development step failed, and what does the course call this failure?
a) Step 2, problem analysis — the programmer did not establish what data he had, where it was, and how the data values were related
b) Step 1, problem description — obtaining the description is complicated because two different parties are involved, the client finding a solution and the programmer providing it, and this description was ambiguous and rested on an unstated assumption about the sort key
c) Step 4, algorithm refinement — the detail added was not matched to who would implement the algorithm and how much knowledge that person had
d) Step 5, algorithm review — a review would have asked whether the algorithm can be applied to more general problems, which would have exposed the wrong sort key

**3.** An algorithm must prompt the user for a number, print "even" or "odd" for it, and keep doing so until the user types 0. Which of the three forms of algorithm representation does it need, and where?
a) Sequence only — the steps are simply performed one after another in the order written
b) Sequence and selection only — the even/odd test is a selection, and "keep prompting" is achieved by writing the prompt-and-test steps out again for each number
c) Sequence, selection and repetition — the ordered steps are sequence, the even/odd test is selection ("if condition is true then perform activity 1 else perform activity 2"), and "until the user types 0" is repetition ("while condition is true do perform activity"), which exists precisely because writing the same step on different lines is not sustainable
d) Selection and repetition only — sequence is a property of flowcharts rather than of an algorithm, since a flowchart is what fixes the order of the boxes

**4.** Before any code is written, an engineer compares two candidate designs by their growth rates and picks one. Six weeks after the chosen design ships in Java, the team measures its actual running time and memory footprint on production traffic. Which is correct?
a) The first is priori analysis — carried out before implementing the algorithm in a particular programming language, and not directly affecting the implementation — and the second is posterior analysis, carried out after implementation and dealing with the space and running-time requirements of the algorithm
b) Both are posterior analysis, because both are concerned with the running time of the algorithm, and running time is what posterior analysis deals with
c) The first is posterior analysis, because its conclusion was acted upon and posterior means "after the decision"; the second is priori analysis with respect to the next version, which it will inform
d) Both are priori analysis, because Big O is a theoretical measure of growth rate and both stages were judged against it

**5. (explain why)** A student claims algorithm P is more efficient than algorithm Q because on the twelve test inputs he tried, P finished sooner. State what the course means by the complexity of an algorithm, name and define the three cases in which time complexity is measured, and explain why the course says the most important factor when comparing two algorithms is the growth rate. Use the course's own 1000N versus N² example to show what the student's twelve timings could easily have hidden.

**6. (explain why)** An in-house procedure is written directly in Python-specific syntax, its main loop has no stated stopping condition, and it prints progress messages but produces no result value. Name the characteristics of an algorithm it fails, stating each in the course's own terms, and explain in each case what goes wrong. Then name two of the course's design considerations that this procedure most clearly ignores, define each, and say why a characteristic and a design consideration are not the same kind of requirement.

## Answers

**1. b** — *Unambiguity: an algorithm must have straightforward and clear instructions, so that the same input determines the same steps.* The course lists as a characteristic that algorithms "should have straightforward and clear instructions", which the summary sheet names **unambiguity**. "Clearly outliers" is not an instruction a machine or a second person can execute identically — it leaves the discarding rule to the reader's judgement, so two faithful implementers legitimately compute different means from the same marks. That divergence is the diagnostic: an unambiguous procedure could not produce it. (a) is the answer of someone who has learned the word **finiteness** without its content: finiteness means the algorithm has a **limited and countable number of instructions**, and having *no* loop makes finiteness easier to satisfy, not harder. (c) is the outright inversion of **language independence**, and is the most-chosen wrong answer here: the characteristic is that an algorithm **should not be dependent on any programming language**, so being written in English is exactly right — that is why algorithms are designed by people and only afterwards converted into a computer program. (d) misreads the **input** characteristic, which requires that the algorithm have input values that are processed to produce some output; a list of unstated length is still an input, and no course requirement fixes its size in advance.

**2. b** — *Step 1, problem description, and its three named failure modes.* The course singles out this step as harder than it looks precisely because **two different parties are involved: the client (finding a solution) and the programmer (providing the solution)**, and it names the three issues that arise — **descriptions relying on unstated assumptions, ambiguous descriptions, and incomplete descriptions**. "Sorts our staff records" is ambiguous about the key and silently assumes the programmer knows which key is meant; nothing downstream can recover from that, which is why the description step comes first. (a) is the near neighbour and the commonest error: **problem analysis** is Step 2 and asks what data we have, where it is, what formulas and rules apply and how the data values relate, so that the **starting and ending points** are clear — but analysis operates on a description already agreed, and here there was no agreed description to analyse. (c) confuses a wrong goal with insufficient detail: **refinement** adds detail to a correct high-level algorithm, judged by who implements it, their knowledge, and the computer specifications — refining the wrong sort key only produces a more detailed wrong answer. (d) is attractive because review does check generality, but Step 5's two questions are whether the algorithm **applies to more general problems** and whether its **complexity can be reduced** — neither asks whether the client wanted something else.

**3. c** — *Sequence, selection and repetition are the three forms an algorithm must exhibit to be easily translatable into various programming languages.* All three appear: the steps run in order and none is skipped (**sequence**); the even/odd decision executes one branch or the other on a condition (**selection**, in the course's `if condition is true then perform activity 1 else perform activity 2` shape); and the whole prompt-and-classify block is executed repeatedly until the sentinel 0 arrives (**repetition**, `while condition is true do perform activity`). (b) is the trap the course itself sets up: the repetition slide exists because **writing the same step on different lines is not sustainable** — you cannot unroll a loop whose number of passes depends on when the user chooses to type 0, since that number is unknown when the algorithm is written. (a) ignores both the branch and the loop and would be right only for a straight-line calculation. (d) confuses a construct with a notation: **sequence** is a property of the algorithm — its steps are ordered so that **no step is skipped unless there is a compelling reason** — and holds equally in pseudocode and in a flowchart, which are merely the two ways of **representing** an algorithm.

**4. a** — *Priori is before implementation in a particular programming language; posterior is after it.* The course's definitions are positional, not qualitative: **priori analysis is carried out before implementing an algorithm in a particular programming language and does not directly affect the implementation**; **posterior analysis is carried out after an algorithm has been implemented in a particular programming language and deals with issues such as the space and running-time requirements**. Comparing growth rates on paper is the first; measuring the shipped Java build on production traffic is the second. (b) is the most tempting wrong answer because it fixes on a true fragment — posterior analysis does deal with running time — and forgets that priori analysis compares running-time growth too; the discriminator is whether the code exists in a language yet, not whether time is being discussed. (c) invents a meaning for "posterior" as "after the decision", which would make every analysis posterior once acted upon and priori again the moment a next version is contemplated — the labels attach to the implementation, not to the decision. (d) makes the mirror-image mistake to (b): Big O is used in both analyses, so the notation cannot be what classifies them.

**5.** *Concept: time and space complexity, the three cases, and growth rate as the basis of comparison.* The **complexity or performance of an algorithm** is analysed in two dimensions: **time complexity, the time required by the algorithm to complete its execution**, and **space complexity, the amount of computer space required by the algorithm to complete its execution**; both are represented by notations such as **Big O**. Time complexity is measured in three cases, each stated for an **input of size n**: **best case** is a measure of the **minimum** time the algorithm will require for an input of size n; **worst case** is a measure of the **maximum** time it will require for an input of size n; **average case** is the time it will require to execute a **typical** input of size n. The student's twelve timings are twelve data points somewhere among these cases at a handful of sizes — they say nothing about which case they landed in, and nothing at all about what happens as n grows. That is why the course states that when two algorithms are compared to know which is more efficient, **the most important factor to consider is the growth rate of both algorithms**, and that **Big O is useful precisely because it describes the growth rate**. The course's own example settles it: compare **1000N** with **N²**. At N = 10 the first costs 10,000 and the second 100, so N² looks a hundred times better; at N = 100 it is 100,000 against 10,000; the two meet at **N = 1000** with 1,000,000 each; and at N = 10,000 it is 10,000,000 against 100,000,000, with the gap widening without limit thereafter. A student timing small inputs would confidently declare the quadratic algorithm the efficient one and be wrong for every input size that matters. The constant 1000 is a fixed multiplier that faster hardware can absorb; the exponent is not, which is why growth rate — not a stopwatch on twelve inputs — decides efficiency.

**6.** *Concept: the characteristics that make something an algorithm, versus the design considerations that make an algorithm good.* The procedure fails three **characteristics**. **Language independence**: the course requires that algorithms **should not be dependent on any programming language**, because an algorithm is a **plan for solving a problem, designed by people**, which **must be converted into a computer program** — writing it in Python-specific syntax collapses the plan into one particular conversion of it, so it can no longer be translated into another language or reviewed independently of Python. **Finiteness**: algorithms **should have a limited and countable number of instructions**; a main loop with no stated stopping condition has no bound on the number of instructions executed, so no one can say the procedure terminates or how much work it does — and Step 5's question "can the complexity be reduced?" cannot even be asked of it. **Input and output**: algorithms **should have input values that will be processed to produce some output**, and the course's very definition is that an algorithm **consists of inputs, a process, and outputs**; progress messages are not the processed result of the inputs, so the output half of that triple is missing. Two **design considerations** it ignores: **robustness**, which the course defines as the **solution to the problem being clearly defined** — an unbounded loop with no result leaves it undefined what solving even means here; and **maintainability**, that the algorithm should be **maintainable and easily refactored** — Python-specific syntax with no separable steps resists exactly that. (**Simplicity**, being **very easy to understand**, and **extensibility**, that **another programmer or designer can update and upgrade it**, would be equally defensible choices.) The two kinds of requirement are not the same: the **characteristics — input, unambiguity, finiteness, effectiveness, language independence — are the conditions for something to count as an algorithm at all**, and failing one means what you have written is not an algorithm; the **design considerations — modularity, correctness, maintainability, functionality, robustness, simplicity, extensibility — are qualities of a well-designed algorithm**, and failing one leaves you with a genuine but poor algorithm. That is why **correctness** appears among the considerations and **finiteness** among the characteristics: an algorithm can be wrong and still be an algorithm, but an endless one cannot.
