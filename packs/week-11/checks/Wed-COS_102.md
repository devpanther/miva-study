**1.** The course defines modularisation as dividing a program's functionality into independent modules **such that each independent module has everything it needs to implement only a part of the program's functionality.** The definition carries two separate conditions. Which design fault does each one rule out?

a) Both conditions rule out the same fault stated twice — a module that is too large — the first by size and the second by scope
b) "Everything it needs" rules out a module that cannot work until other modules assist it, which is coupling; "only a part" rules out a module that has taken on more than one part of the functionality, which is cohesion
c) "Everything it needs" rules out duplicated code, since a module that has everything need never copy from elsewhere; "only a part" rules out a module being reused in a second program
d) "Everything it needs" requires every module to hold its own copy of the program's data; "only a part" requires that no module be visible to any other

**2.** The course opens with a function of more than five thousand lines and asks how stressful it would be to change part of it. What, precisely, is the fault being complained of?

a) That the function is too long to read in one sitting, so no single developer can hold it in mind well enough to work on it
b) That a function of that size will exceed the compiler's limits and must be broken up before it will build at all
c) That changing a part of the code can affect other parts of the code, so no change can be made in isolation — which is why the stated cure is being able to change different parts without affecting other parts
d) That a five-thousand-line function must contain duplicated code somewhere, and duplication is the fault that decomposition exists to remove

**3.** A team modularises a working program. Afterwards the build takes noticeably longer, the compiled program is larger, and it runs slightly slower. What should they conclude?

a) That these are three of the course's five stated disadvantages of modularisation itself — the price paid for the advantages, incurred by the module boundaries that control and data must now cross
b) That they have produced low cohesion, since a slower and larger program is the standard symptom of functions that do not serve one aim
c) That they have produced high coupling, since a longer build means the modules are being recompiled because of one another
d) That they have modularised something that should not have been modularised, since a correct modularisation leaves execution time, size and build time unchanged

**4.** Cohesion is judged by which question?

a) How many other modules this module has to call before it can complete its work
b) How frequently the functions inside the module call one another, since a module whose functions never call each other has not been joined together at all
c) How small the module is, since the course's advantages are all stated of smaller modules and functions
d) Whether the functions in the module work together to achieve the ultimate aim of the module — so functions that never call one another are cohesive if they serve that one aim, and functions that call each other constantly are not if they are collectively serving several

**5.** Module `report` contains a single line that reads `records[cid][7]` from module `customer`, and nothing else. Module `invoice` calls three published functions of `customer` two hundred times. On the course's definition, which is more tightly coupled to `customer`?

a) `invoice`, because coupling describes the extent to which modules depend on one another and two hundred calls is a far greater extent of dependence than one
b) `report`, because coupling is the extent to which a module depends on another before it can perform its function, and `report` depends on `customer`'s internal data structure and field order, which changes whenever `customer` is reorganised
c) They are equally coupled, since both reach outside themselves and coupling records only whether a dependency exists, not what it is on
d) Neither is coupled at all, because coupling is a property measured between whole subsystems, whereas both of these are single modules within one subsystem

**6.** Which statement about information hiding is correct?

a) Modules should pass as little information to one another as they possibly can, and a module that receives less than it needs is preferable to one that receives more
b) Information hiding means the source code of a module is kept from other teams, which is why the course lists it among the security measures of a design
c) The data structures and processing details of one module are not accessible to other modules, and modules pass only that much information as is required to accomplish the software functions
d) Information hiding is the practice of storing each module in its own file so that a developer working on one module cannot see the contents of another

**7.** Designer A splits a module that had been doing four loosely-related jobs into four modules; for every input the system's outputs are identical to before. Designer B changes a module so that it now also emails a receipt. Which has refactored, and what is the test?

a) Both have: each has improved the design, and refactoring is any change made to improve the internal quality of a system
b) A only: refactoring modifies a software system to improve the internal structure of design **without changing its external behaviour**, and B's change is externally visible
c) B only: A has merely moved code between files, and refactoring requires that the design be genuinely improved, which splitting alone does not achieve
d) Neither: refactoring means reducing the complexity of module design, and A increased the number of modules while B added work

**8.** Which single feature separates an **idiom** from an architectural pattern and a design pattern?

a) It is the only one of the three that is intended to be reused, the other two being descriptions of a particular system rather than solutions to recurring problems
b) It is the only one concerned with the interaction between software components, the other two being concerned only with structure
c) It is the smallest, being a pattern that occupies fewer lines than a design pattern, which in turn occupies fewer than an architectural pattern
d) It is programming-language specific — it describes the implementation of a component, and the method of interaction among components, in a specific programming language, which is why idioms are also called coding patterns

**9. (explain why)** Define **cohesion** and **coupling** in the course's words. For each, say where the measurement is taken and which direction it should go. ## Answers

**1. b.** *Concept: the definition of modularisation states the coupling condition and the cohesion condition in one sentence.* "Each independent module has **everything it needs**" is the demand for independence — a module that must first ask another module for help does not have everything it needs, and that is exactly **coupling**, "the extent to which modules depend on other modules before performing their function". "To implement **only a part** of the program's functionality" is the demand for one job — a module implementing two parts is the module the **single responsibility principle** forbids, and it is exactly low **cohesion**. (a) reads both halves as being about size; neither mentions size, and a large module can satisfy both while a tiny one can fail both. (c) borrows Week 8's "prevents the duplication of codes", which is a benefit of writing a function once, not a clause of this definition — and the second half inverts a stated *advantage*, since the course says modules can easily be used **in another program**. (d) makes two impossible demands: duplicating the program's data in every module would guarantee inconsistency, and modules invisible to one another could never be assembled into a program.

**2. c.** *Concept: the stated problem is change propagation, not length.* The deck's sentence is "**changing a part of the code can even affect other parts of the code**", and the cure it states is the exact negation: modularisation "**ensures that we are able to make changes to different parts of our code without affecting other parts of the code**". Length is only how the entanglement is noticed. (a) is the plausible half-truth that costs the mark: readability is a listed **advantage** of modularisation ("understanding a small module and function is easier"), but it is not the fault the five-thousand-line slide is about, and a five-thousand-line function that touched nothing else would still be readable one screen at a time. (b) invents a compiler limit; nothing in the deck concerns compiler capacity, and the deck in fact lists longer **compilation** time as a disadvantage of modularising. (d) assumes duplication must be present; a long function may contain no duplication at all and still be impossible to change safely, which is why the deck's complaint is stated in terms of effects, not repetition.

**3. a.** *Concept: the five disadvantages are the cost of modularisation as such.* The course lists them: **execution time may be longer, storage size may be increased, compilation and loading time may be longer, inter-module communication problems may be increased, and it demands more initial design time.** Each is caused mechanically by having boundaries at all — a boundary is a place control and data must cross, and separately stored, separately compiled units are separately loaded. (b) and (c) are the vocabulary answers: they reach for the two words everyone remembers and attach them to symptoms that are not diagnostic of either. Low cohesion shows itself as a module that cannot be described in one phrase; high coupling shows itself as a change in one module forcing changes in another. Neither is measured on a stopwatch. (d) states the opposite of the deck — if modularisation were free of cost there would be no disadvantages slide, and no reason for the deck to warn that it **demands more initial design time**.

**4. d.** *Concept: cohesion is judged against the module's single ultimate aim.* The definition is that cohesion "describes the extent to which the functions in a module work together to **achieve the ultimate aim of the module**". The test therefore names an *aim* and asks whether every function serves it. (a) is the definition of **coupling**, and it is asked outward rather than inward — the single commonest confusion in the topic, and the reason so many scripts answer both questions with the same sentence. (b) is the trap this question exists for: mutual calling is neither necessary nor sufficient. `validate` and `send_confirmation` in a user module never call each other and both serve one aim; the deck's own refactoring example is a component whose four functions have "a **limited relationship** with one another" — the fault is four aims, not silence between them. (c) confuses cohesion with size; the advantages of smallness are listed separately, and a small module holding two unrelated functions has low cohesion precisely because it is not small enough to have one aim.

**5. b.** *Concept: coupling counts what a module must depend on, not how often it speaks.* Coupling is "the extent to which modules depend on other modules **before performing their function**". `report` cannot perform its function unless `customer` stores records in a structure indexed by `cid` with the discount in field 7 — so it depends on `customer`'s **data structures**, which is exactly what information hiding says must not be accessible. Reorder the fields, or move the records into a database, and `report` breaks, silently, while still compiling. `invoice` depends only on three published functions continuing to answer the same questions; two hundred calls change nothing about what it must know. (a) is the "coupling means traffic" belief, which counts the wrong thing entirely and would make every well-designed system look tightly coupled. (c) reduces coupling to a yes/no, but the word is *extent* — it is precisely a matter of degree, and the degree is set by what is depended upon. (d) invents a rule that coupling applies only between subsystems; the deck states it of modules in a project.

**6. c.** *Concept: what information hiding hides, and the word "required".* The deck: "**the data structures and processing details of one module are not accessible to other modules**", and modules "**pass only that much information to each other, which is required to accomplish the software functions**". (a) is the most instructive wrong answer, because it is the same sentence with **required** deleted. Passing less than is required does not hide anything; it produces a module that cannot do its job, and the deck's phrasing sets the floor at what the functions need. (b) is the Week 8 error at module scale: hiding is about what other **code** may reach and depend upon, not about who may read the source — perfectly public source can still hide its data structures behind an interface. (d) confuses a file with an interface. Putting modules in separate files is described by the deck as something modularisation permits; it hides nothing if the second module can still read the first one's structures.

**7. b.** *Concept: refactoring is defined by unchanged external behaviour.* "Refactoring can be defined as a process of modifying a software system to improve the internal structure of design **without changing its external behaviour**" — and it "reduces the complexity of module design **while keeping its behaviour or function unchanged**". A's split leaves every output identical, which is exactly the deck's own worked example: a component with **low cohesion** performing four functions of limited relationship is refactored into four components each with high cohesion, leading to easier integration, testing and maintenance. B's receipt email is a new externally observable act, so whatever its merits it is not a refactoring. (a) drops the defining clause and calls any improvement a refactoring — which destroys the point of the word, since refactoring's whole value is the promise that if behaviour changed, something went wrong. (c) demands that the design be "genuinely improved" by some other test; the deck's improvement is precisely the move from low to high cohesion, which is what A did. (d) misreads "reduces the complexity of module design" as "reduces the number of modules"; the deck's example *increases* the count from one to four and calls that a reduction in complexity.

**8. d.** *Concept: the level and the language-dependence of the three pattern types.* Idioms are "**low-level patterns, which are programming-language specific**"; they "describe the implementation of a software component, the method used for interaction among software components, etc., **in a specific programming language**", and are "often termed **coding patterns**". That is the only property that separates them cleanly. (a) inverts the definition of a pattern altogether: a pattern is by definition "a description of the solution to a recurring design problem... in such a way that the solution can be **used again and again**" — reusability is common to all three. (b) is a real trap, because design patterns explicitly address "**mechanisms that affect component-to-component interaction**"; interaction is therefore not the discriminator, and an answer that reaches for it has read only the idiom slide. (c) invents a size ordering. High, medium and low describe the **level of strategy** — architecture, refinement of elements, implementation — not the number of lines; an architectural pattern may be a paragraph and an idiom a page.

**9.** *Concept: cohesion and coupling — two readings, two places, opposite directions, and why merging is a counterfeit fix.* **Definitions.** **Cohesion** "describes the extent to which the functions in a module work together to achieve the **ultimate aim of the module**", and "we usually want **high** cohesion between the functions in a module". **Coupling** "describes the extent to which **modules depend on other modules** before performing their function", and "since we want our modules to be independent, we usually want **low** coupling between the modules in a project". **Where each is measured.** Cohesion is a reading taken **inside a single module**: name the module's one aim, then ask of each function whether it serves that aim. Coupling is a reading taken **between modules**: name the boundary, then ask what one module must know about the other before it can work. Because they are taken in different places, they are not two ends of one scale, and a design can be bad on both at once. **Why merging is not an improvement.** Suppose `orders` calls `stock` and a team merges them into `sales`. The coupling between `orders` and `stock` is now zero — but only because there is no longer an `orders` and a `stock` to measure between. The dependency itself has not been removed: the same code still needs the same information at the same moment. What has changed is that it now runs **inside** a module, where no interface governs it and no one can see it; the boundary that used to make the dependency explicit, reviewable and narrow has been deleted rather than tightened. At the same time cohesion has fallen, because `sales` now has two responsibilities and so breaks the deck's single responsibility principle — "modules should not have more than a single responsibility". The genuine fix is the opposite operation: keep the boundary and **narrow the interface**, so that `orders` depends on one published question rather than on `stock`'s internals. The test to apply is not "did a number improve" but "if `stock` is reorganised internally, must `orders` change?" **The car analogy.** The car transports passengers; the steering wheel, radiator, battery and brake each exist for **one aim** — steering, cooling, storing charge, stopping. None of them has a second job, so each is **highly cohesive**, and that is why a fault can be diagnosed to a part and a part replaced on its own. The starter, however, plainly **depends** on the battery, so the parts are not independent in the sense of being unconnected — and this is the point students miss. What makes the coupling **low** is that the starter needs only **twelve volts at two terminals**: it does not know the battery's chemistry, its plate arrangement or its internal wiring, so a different battery of the same terminals works and no part of the starter changes. Low coupling is therefore a real dependency running through a **narrow, defined interface**, not the absence of dependency; a part that depended on nothing would do nothing.

**10.** *Concept: information hiding — what is hidden, from whom, and why it is the cause of low coupling.* **The definition.** "Modules should be specified and designed in such a way that **the data structures and processing details of one module are not accessible to other modules**. They pass only **that much information to each other, which is required to accomplish the software functions**. The way of hiding unnecessary details is referred to as **information hiding**." **The three benefits.** "It **emphasises communication through controlled interfaces**"; "it **decreases the probability of adverse effects**"; "it **restricts the effects of changes in one component on others**." **What is hidden, from whom, and what still crosses.** What is hidden is the **data structures** — how the module stores what it stores — and the **processing details** — how it does what it does. From whom: from **other modules**, i.e. from other *code*. What still crosses the boundary is the module's **service**, and exactly as much information as the software functions **require**; the word *required* sets a floor, so information hiding is never an argument for starving a caller of what it needs. The interface is deliberately kept, not shrunk to nothing. **Why it is the mechanism, not a separate habit.** Coupling is "the extent to which modules depend on other modules before performing their function", and a module can only depend on what it can **reach**. If the data structures and processing details are inaccessible, then no other module *can* be written to depend on them, however careless its author; the only thing left to depend on is the published interface, which is why the first stated benefit is that communication is forced **through controlled interfaces**. The third benefit then follows automatically — if nothing outside depended on the internals, changing the internals **restricts the effects of changes in one component on others** to nothing at all. So low coupling is not achieved by exhortation but by inaccessibility: information hiding removes the *possibility* of the dependency, and low coupling is the reading you take afterwards. It is also the same bargain as Week 8's functional abstraction — a caller gets a name and the input and output formats — stated one scale up, at the module rather than the function. **The common misreading.** That information hiding means keeping the source code secret from people. It does not: the target is other **modules**, and a module whose source is published in full still hides information if nothing outside it can reach its structures. The second, subtler misreading is treating "pass only that much information" as "pass as little as possible" — the sentence ends "**which is required to accomplish the software functions**".

**11.** *Concept: software architecture and the three levels of software pattern.* **Software architecture** "refers to the **structure of the system**, which contains **various components** of a program or system, the **attributes (properties) of those components**, and the **relationship between them**". All three parts are examinable, and an answer naming only the components has given a third of the definition. The course adds that "the software architecture enables the software engineers to **analyze the software design efficiently**". **Why we need it — the three stated reasons.** It "**enables efficient communication between all the interested stakeholders**"; it "**highlights early design decisions that affect activities such as coding and testing**"; and it "**creates intellectual models of how the system is organized into components and how these components interact with each other**". Note that all three are about people and foresight: an architecture is a thing to talk about and to decide with, before there is code to inspect. **Software pattern, generally.** A pattern "provides a description of the solution to a **recurring design problem of some specific domain** in such a way that **the solution can be used again and again**"; its objective is to give a designer insight enough to determine whether the pattern **can be reused**, whether it is **applicable to the current project**, and whether it can be used to develop **a similar but functionally or structurally different design pattern**. **The three levels.** **Architectural patterns** are **high-level strategies** referring to the **overall structure and organization** of a software system; they **define the elements** of a system — subsystems, components, classes — and **indicate the relationship between the elements along with the rules and guidelines for specifying these relationships**. They are **often considered equivalent to software architecture**. **Design patterns** are **medium-level strategies used to solve design problems**; they provide a means for the **refinement of the elements** defined by an architectural pattern, or of the relationships among them, and they address **specific design elements such as the relationship among components or mechanisms that affect component-to-component interaction**. They are **often considered equivalent to software components**. **Idioms** are **low-level patterns** which are **programming-language specific**; they describe **the implementation of a software component and the method used for interaction among software components in a specific programming language**, and are **often termed coding patterns**. The ordering is therefore one of decreasing scope and increasing commitment: architecture says what the parts are, design says how a part is refined and how parts interact, and the idiom says how that is written in C or Python.

**12.** *Concept: the two design approaches, and why each alone fails.* **Top-down design** starts by taking **the whole software system as one entity** and **decomposes it** to achieve more than one sub-system or component **based on some characteristics**. Each sub-system is then **treated as a system in its own right and decomposed further**, and the process **keeps running until the lowest level of system in the top-down hierarchy is achieved**. In the course's phrasing, it "starts with a **generalized model** of the system and keeps on defining the **more specific** part of it", and "when all components are composed the whole system comes into existence". It is **more suitable when the software solution needs to be designed from scratch and specific details are unknown** — which is precisely the situation in which you can describe the whole but not yet the parts. **Bottom-up design** "starts with the **most specific and basic components**", then "proceeds with composing higher-level components by using basic or lower-level components", and "keeps creating higher-level components **until the desired system is evolved as one single component**". Here "**with each higher level, the amount of abstraction is increased**" — you climb away from the specifics. It is **more suitable when a system needs to be created from some existing system, where the basic primitives can be used in the newer system**, i.e. when the parts already exist and the question is what to build out of them. **Why neither is individually practicable.** The course states it flatly: "top-down and bottom-up approaches are **not individually practicable**; instead, a **good combination of both is used**." The reason is that each runs out of information at the end furthest from where it started. Pure top-down keeps subdividing on the assumption that whatever a sub-problem needs will exist when it gets there; at the bottom it meets the primitives that actually exist — the libraries, the database, the hardware, the modules already written — and if these do not match the shape the decomposition assumed, the split has to be redone, and the deeper the hierarchy the more of it is wasted. Pure bottom-up has the opposite failure: it composes excellent, highly cohesive components upward without any statement of the system's ultimate aim, so it can produce a fine set of parts that assemble into the wrong system, or into one whose top-level structure nobody can describe to a stakeholder — which is exactly what the architecture slide says an architecture is for. In practice the top-down decomposition supplies the aims and the boundaries, the bottom-up composition supplies the primitives and the reality check, and the design converges from both ends: this is also why the week's other topics matter to both, since whichever direction you travel in, the cut you make is judged by cohesion, coupling and information hiding.
